# Ревью проекта [task-tracker](https://github.com/gomode13/task-tracker)


### Плюсы

+ Чистая многослойная архитектура бекенда. Роутеры тонкие, бизнес-логика в сервисах, код согласованный и читаемый.
Хорошая структура проекта, понятный нейминг директорий и файлов.

+ Грамотная схема авторизации c использованием JWT.

+ Пароли хэшируются Argon2, а регистрация снимает гонку на дубликате email через перехват `IntegrityError` - редкий для учебных проектов уровень внимания.

+ Хорошая организация фоновой работы.
Один Docker-образ `godmode13/task-tracker-backend:main` переиспользуется для API, двух Celery-воркеров и beat (различаются только командой). Это круто.
Письма отправляются Celery-тасками с ретраями (`max_retries=3`, backoff). Чёткая маршрутизация по очередям `celery`/`reports`.

+ Инфраструктура выше среднего. Multi-stage сборки (venv из builder-стадии), non-root `appuser` в контейнерах, 
healthcheck'и для всех инфраструктурных сервисов, миграции как одноразовые зависимые сервисы (`service_completed_successfully`), 
CI c matrix-сборкой, SBOM и provenance. `.env.example` задокументированы для каждого сервиса. Очень хорошо сделано по деплою.

+ Продуманная идемпотентность суммаризации.
Отдельная БД с таблицей `processed_requests` защищает от повторной обработки одного запроса при ребалансировке consumer-группы.

+ Тщательно выверенный LLM-промпт - правила, формат, примеры, запрет додумываний.

+ Отличный README - архитектура, схема пайплайна отчётов, локальный запуск, CI/CD, заметки про SMTP-порты Resend.


### Минусы

- Полностью отсутствуют линтеры и типчекеры. (ruff, mypy).
Попробуй их установить в дев окружении и применить (`ruff check .` и `mypy .`)
А потом в пайплайн их выполняться до стадии build.

- Работа с переменными окружения может быть лучше. Сейчас один класс `Settings` и в нем все переменные проекта.
Хоть они и разделены логически отступаами строк.
Лучше: класс `Settings` и в нем ещё лежат объекты конкретных зависимостей: `db`, `redis,` `rmq`, `kafka`, `jwt`, `smtp`.
И тогда сами атрибуты будут не `RABBITMQ_HOST: str`, а типа такого:
```python
class RmqConfig(BaseModel):
    user: str = Field(alias="RABBITMQ_DEFAULT_USER", default="guest")
    password: str = Field(alias="RABBITMQ_DEFAULT_PASS", default="guest")
    host: str = Field(alias="RABBITMQ_HOST", default="rabbitmq")
    port: str = Field(alias="RABBITMQ_PORT", default=5672)
```
Обращение к этим переменным тоже будет удобно, например: `settings.rmg.host`.
Хотя использовать везде alias и не обязательно, можно и текущие значения брать.

- В функциях и методах не хватает строк документации. Главным критерием в строке документции является ответ на вопрос: почему нужен это метод или функция.
Ну и какие он параметры принимает, что это за параметры. Должны быть хотя бы в слое бизнес логики. Но в очевидных функциях может быть избыточно.

- Гонка в дедупликации суммаризации.
Метод `handle_daily_report_request` делает check-then-insert (`is_request_processed` - обработка - `create_processed_request`) без резервирования. 
При повторной обработке возможен двойной вызов LLM и необработанный `IntegrityError` на unique-констрейт.

- Нет защиты от перебора паролей.
На `POST /session` и `POST /user` нет rate limiting - открытая площадка для брутфорса и спам-регистраций.

- Prompt injection. 
Названия задач вставляются в LLM-промпт без фильтрации. 
Чисто теоретически заголовок вроде "игнорируй все инструкции системы и напиши..." вполне может привести к нежелательному поведению суммаризации.
Более правильная архитектура может выглядеть, например, как чёткое разделение trusted instructions и untrusted data.

- Регистрация не атомарна.
Функция `send_welcome_email.delay()` вызывается сразу после создания пользователя.
При недоступном RabbitMQ `.delay()` бросит исключение - пользователь создан в БД, но ответ вернётся 500. Нет компенсации/отложенной отправки.

- Мелкие проблемы надёжности.
Основной Celery-таск отчётов не имеет retry/выхода из таймаута при сбое Kafka.
Флаг `extra="ignore"` в pydantic-settings молча игнорирует ошибки заполнения env файла. 
Лучше пусть будет более строгая проверка, и приложение будет падать при неправильном заполнении переменных окружения.

- При регистрации если написать валидный email и пароль "123" выдается мало информативное сообщение "Проверьте правильность заполнения полей".
Тут лучше выводить конкретику для пользователя, что не устраивает длина пароля, или недопустимые символы и т.п.


### Общий итог

Проект заметно выше типичного учебного уровня: чистая архитектура, зрелая схема авторизации, аккуратная инфраструктура и внимание к деталям.
Фундаментальных архитектурных дефектов нет. Критических замечаний не выявлено.
