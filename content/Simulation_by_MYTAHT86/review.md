# Ревью проекта [Simulation](https://github.com/MYTAHT86/Simulation)

## Плюсы:

+ Чистая ООП-архитектура: Хорошее использование наследования (Entity -> Creature -> Herbivore/Predator, Actions как абстрактный класс). 
Классы имеют чёткие ответственности. Видно, что смотрел и изучал типовые замечания на этот проект.

+ Модульная структура: Проект разбит на логические модули (map, creatures, bfs, actions, makers, checkecosystem), что облегчает навигацию.

+ Реализация BFS: Корректная реализация поиска кратчайшего пути в консольной среде для поиска цели.

+ Сбалансированная экосистема: Механика голода у хищников и воспроизводство/появление объектов в CheckEcoSystem поддерживает симуляцию.

+ Управление симуляцией: Возможность паузы/возобновления/остановки через консольные клавиши (p/c/e).

+ Гибкая генерация мира: Случайная расстановка препятствий, травы и существ при старте.

+ Переиспользуемые абстракции: Actions как интерфейс для активации, BFS как утилита поиска.


## Минусы:

- В `Map.delete_on_map()` при передаче `step_to_make` происходит `del Map.collection[current_location]` без проверки существования ключа.
Это может вызвать `KeyError`. Всегда перед такими операциями надо проверять.

- В `BFS.search()` используется `pop(0)` (O(n)) - для 16x16 карты не критично, но лучше использовать deque.
Причем круто бы реализовать эту очередь без использования модуля collections.

- В `Herbivore.lose_hp()` при смерти может быть проблема, если `self.eating_status` истинно, но `self.nearest_grass` отсутствует.

- В `Map.find_current_slot()` использует `next()` без обработки случая отсутствия - может бросить StopIteration при рассинхронизации коллекции/карты.

- Много статических классов/методов (Map, Simulation) - больше похоже на модули глобального состояния, нежели на экземплярные объекты. 
Это трудно тестировать и расширять. В идеале сделать так, чтобы при добавлении новой сущности и новой логики не пришлось трогать классы Map, Simulation.

- Циклические импорты предотвращены через TYPE_CHECKING, но структура всё ещё хрупкая (многие модули зависят друг от друга).
Тут очевидно, что классы сущностей ничего не должны знать про карту, на которой они живут.
Также они ничего не должны знать про алгоритм BFS.
Класс симуляции знает про сущности, про карту и про BFS, и применяет их.

- Качество кода: присутсвтуют неиспользуемые импорты, отступы не везде выдержаны и т.п.
В пакете map название файла `__init.py` с опечаткой. 
Отсутствуют типы в некоторых местах. Например, в `Map.collection` используется смешивание с None, которого там быть не должно. 

- Метод `check_location` чтобы вернуть bool достаточно проверить существование переменной `Map.collection` без ключей этого словаря.
В методе `is_slot_free` тоже самое. Посмотри как работает приведение типов в python (на собеседованиях потом пригодится).

- Магические числа 16: если есть какое-то статическое число, то его лучше вынести в константу.
По другим числам тоже самое. 
Если будет где-то лежать файл config.py и в нем будут все константы собраны, которыми можно будет регулировать размер карты, количество сущностей, hp и прочие параметры симуляции. Это будет удобно.
