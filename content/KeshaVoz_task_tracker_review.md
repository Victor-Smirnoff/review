# Ревью проекта task_tracker


По примечаниям к проекту:

п.1. ок, фронт не смотрим, не наше это дело.

п.2. Пытаюсь понять эту боль с валидацией данных форм.
Здесь происходит три операции: получение данных из HTTP (Form) -> преобразование данных -> валидацию Pydantic.
Если данные формы не соответствуют своей спецификации, то фаст апи вернет 422 - RequestValidationError.
А никак не 500. 500 может вернуться если ошибку ValidationError поднимет Pydantic.
Самый простой вариант - отказаться от типа данных dict и не возвращать его через as_form. 
Пусть Depends будет возвращать саму модель. 
Сам return в методе as_form обернуть в try-except и там ловить этот ValidationError.
В роутера убрать try-except, так как эта ошибка будет ловиться в as_form.
Обработчик уже будет работать с валидной моделью.


Плюсы:

+ Код написан аккуратно и логично.

+ Хорошая структура проекта, понятно что где лежит. Для каждого приложения есть Dockerfile и entrypoint.

+ Докер файл с multi-stage сборкой, это best practice. Написан хорошо.

+ Докер компоуз тоже хорош. Есть отдельный девелоп и отдельный для прода. Для сервисов есть `healthcheck`, это хорошая практика для production.

+ Во всех функциях и методах есть аннотации типов, это прям обязательная практика.

+ Чанкование данных при обработке пользователей из БД. Хорошая практика. Защита от переполнения оперативной памяти.

+ Настроено логирование в проекте. Это хорошо помогает дебажить и искать причины ошибок.

+ Есть обработчики всех HTTP, FastAPI, Starlette ошибок. Только почему-то не совсем правильно они используются.
Имеется ввиду что в каждой ручке все равно оборачивается в `try-except` получение `validated_data` из `form_data`.

+ В LLM сервисе есть защита от промт-инъекций, присутствует идемпотентность (проверка кеша), базовые уязвимости учтены. 

+ Наличие тестов.


Минусы:

- Может это не совсем минус, но всё же - совмещение разных приложений в одном репозитории. Имею ввиду основной app, summarization-service и task-tracker-frontend.
В реальных проектах это всё разные репы со своими ветками, деплоями, ci и прочим. Хотя бывает и множество проектов монорепо. Вкусовщина, за минус не считается.

- Избыток зависимостей в файле `requirements.txt`. Залетело всё что попало, видимо создавался он через `pip freeze -> requirements.txt`,
там должно быть минимально необходимое количество зависимостей, а не вообще все, которые используются в проекте.
Есть группа основных зависимостей, которые мы там указываем, а остальные подтягиваются сами как зависимости у основных.
Например `fastapi` использует внутри себя `starlette`, поэтому `starlette` можно исключить. 
Проверить можно просто: удалить из проекта все либы, оставить только pip, а в requirements оставить одну строчку `fastapi==0.134.0`,
после чего установить всё из этого файла, и так будет список из нескольких библиотек, от которых зависит `fastapi`.
В другом сервисе `/summarization-service/requirements.txt` уже зависимости выглядят сильно лучше.

- Проверить используется ли библиотека `psycopg2-binary` или нет. В примере переменных окружения `DATABASE_URL` ссылается на `asyncpg`.

- Конфиг можно сделать более удобно. Не все переменные в одном классе `Settings`, а сделать этот класс общим сеттингом.
А для каждого вида сеттингов создавать отдельные классы, объекты (db, redis, smtp, jwt и т.д.) которых и положить в общий `Settings`.
Будет тогда что-то типа такого:
```python
class Settings(BaseModel):
    db: DBConfig = DBConfig(**env)  # можно объект прямо тут создавать
    redis: RedisConfig = Field(default_factory=load_redis_config)  # а можно объект создавать через вспомогательную функцию
    smtp: SMTPConfig = SMTPConfig(**env)
```
Такой подход позволяет удобно ориентироваться и использовать эти переменные: `settings.db.host`, `settings.redis.host` и так далее.
Тоже самое касается конфига для приложения `summarization-service`. 
Разделить на три разных класса конфига: кафка, БД, ллм.
Здесь ещё создается объект `SettingsConfigDict` с несуществующим параметром `env_file_ignore_missing=True`.
Это скорее просто опечатка. 
А вообще Pydantic ищет сначала в проекте файл `.env`, если не указать точный путь, то по всем директориям проекта ищет.
Если файла не находит, то идет искать в системные переменные окружения.
Передача переменных через `.env` файлы годится только для локального запуска. В проде обычно системные переменные окружения используются.

- Импорты не в самом топе файлов. Есть причина делать именно так ? Все импорты должны быть обычно в топе файла.
Бывают редкие исключения, когда импорты не в самом топе
В проекте есть также неиспользуемые импорты, их обычно линтеры отлавливают, и код не пойдет в ci, пока такие нечеты не будут устранены.
То есть первая джоба в пайплайне - это линтеры (их может быть несколько), потом уже стадия build, и потом разворачивание деплоя.

- В файле `app/tasks/email.py` есть запись выражения в одну строку `if not user_ids: break`, лучше избегать такого стиля, переноси `break` на следующую строку.
Тут тоже так `app/schemas/tasks.py` в одну строку:
```python
if title is not None: form_data["title"] = title
if text is not None: form_data["text"] = text
```
Чаще используют многострочную запись — она лучше читается. PEP8 не рекомендует.

- В `__init__.py` используй переменную `__all__`. В неё списком складывай имена импортируемых классов и функций.
Это поможет явно контролировать импорты у пакетов.
Вообще в проекте не хватает `__init__.py` для всех директорий. Явное лучше не явного.
Благодаря твоему проекту я узнал, что PEP420 изменил правило создания пакетов, где теперь `__init__.py` не требуется.
Но всё же буду рекомендовать по старому использовать `__init__.py`. Минимально пустым файлом. А по-максимуму там можно целые гирлянды различной логики писать.

- /app/auth/token_service.py в методе _create_jwt это скорее staticmethod, чем classmethod.

- Смешение слоев. В классе `TokenService` есть метод `create_auth_response` и `create_refresh_response`, который собирает объект `Response` из `from fastapi import Response`.
Сервис не должен ничего знать о деталях HTTP-доставки. Всё что касается HTTP должно быть в эндпоинтах. 
Завтра будем возвращать по gRPC или в JSON, то придется переписывать сервис. А если оно сразу будет в эндпоинтах, то изменения сервиса не коснутся.

Здесь же в классе `TokenService` есть повторяющиеся параметры `httponly, secure, samesite`. 
Их все надо бы вынести в класс `CookieConfig`, чтобы при изменении политики безопасности не менять код во всех местах, а поменять только в конфиге.
Они же используются в SilentRefreshMiddleware.
Ну и флаг `secure=True` для продакшена вариант.

- Класс для редиса. /app/redis_client.py здесь лучше не использовать глобальные переменные, а создать класс RedisManager, у которого будут свойства pool и client, которые в интите будут None.
После чего метод init_redis будет уже в классе, вызывать его там же в lifespan. С классом будет чуть удобнее этим пользоваться.
Тоже самое замечание касается /app/tasks/email.py. Здесь удобно будет сделать класс EmailReportManager и не использовать global.
Это замечание может быть и не минус вовсе, просто через классы будет красивее. Хотя такой подход тоже имеет место быть.

- Аннотации типов через `Optional`. Сейчас с версии python 3.10+ уже нужно не использовать `Optional`, а писать `str | None` вместо `Optional[str]`.
В целом можно использовать и `Optional`, оно работает, но новый подход современнее.

- Получение bool значения. /app/schemas/tasks.py тут есть `form_data["is_completed"] = isCompleted.lower() == "true"`
Сложная конструкция, сравнивать строки, приводить их к lower(), если pydantic сам умеет парсить bool.
`form_data["is_completed"] = isCompleted` даст тот же результат.
Здесь же чтобы не использовать неправильный нейминг в методе as_form для isCompleted, надо вместо `isCompleted: Optional[str] = Form(None)` сделать так
`is_completed: bool | None = Field(default=None, validation_alias="isCompleted")`
        
- Нейминг классов. STaskIn, STaskOut и STaskUpdate можно и подробнее назвать, чтобы было более понятно к чему они относятся.

- В брокере сообщений надо очень аккуратно относиться к `enable_auto_commit=True`. Тут используем только False. 
А коммитим сообщения только после его обработки в ручную.
Помечать сообщение прочитанным можно только в том случае, когда оно было обработано.
Здесь если скрипт упадет на выполнении обработки `for msg in consumer`, то часть сообщений будет удалено, но не обработано.

- Танцы с бубном на sys.path. Проект запускается видимо не правильно.
Здесь такого быть не должно, скрипт надо правильно запускать как модуль, тогда пути настроятся автоматически, и не придется ничего городить с sys.path.

- BaseDAO. Самый критичный недочет в проекте. Хорошая практика сделать базовый класс и в нем все методы для получения, добавления, удаления данных.
Но здесь один жесткий минус - в каждом методе создается новая сессия. Это антипаттерн. 
В большинстве случаев это усложняет управление транзакциями, поэтому чаще передают Session извне.
Основная идея в том, что если мы создаем пользователя, его профиль, и ещё что-то, то будем делать это в разных транзакциях.
А нам хотелось бы делать это всё в одной транзакции: создать либо всё сразу, либо ничего.
Для решения этого вопрос надо в BaseDAO сделать __init__ и в него положить параметр self.session.
Теперь каждый метод может использовать этот self.session.
А получение сессий сделать отдельной функцией или методом в классе DataBase (кстати, database.py - тут тоже лучше класс создать и в нем этот метод)

В классах наследниках UserDAO и TaskDAO тоже убираем создание сессии, и используем self.session.
Тоже самое по созданию сессии касается и приложения `summarization-service` в его dao слое.

Методы синхронной работы add_sync, find_all_sync, они нигде по коду не используются, можно их удалить.

- Метод find_all_ids_chunk может пропускать айдишники пользователей.
Если в процессе работы этого метода будет добавлен новый пользователь? тогда одного пропустим
Или удален старый пользователь. Тогда одному юзеру send_daily_report прилетит два раза.
Тут надо полностью убрать offset и переписать код на фильтрацию по первичному ключу (id > last_id).
То есть искать все айди пользователей, которые больше последнего обработанного.

- Функция-обработчик ошибок fastapi_validation_exception_handler возвращает клиенту почти в исходном виде error_msg.
Это не хорошо. Клиенту надо возвращать что-то из пользовательских ошибок, а не код приложений, базы данных и т.п.
Клиент ничего не должен знать про наш код. Конкатенация с "->" прикольно смотрится. 
Здесь надо только посмотреть на выражение с loc_data, если в этой переменной будет пустой список.
А вообще эта функция хороша, делает именно то, что надо - логирует ошибки.

- Класс SilentRefreshMiddleware. 
Строчка `if (not user_id or should_refresh_access) and refresh_token`
Здесь получается интересная история - если access_token просрочен и сработает `except jwt.ExpiredSignatureError` и `should_refresh_access = True`,
`user_id = None` таким и останется, то это условие всегда выполнится в левой его части, оно избыточно. 
Переменная `should_refresh_access` тут просто дублирует суть not `user_id`. И точнее условие написать прямо так: `if user_id is None`.
Вложенные конструкции `try-except` следует избегать, если они есть, то присутствует смешивание ответственности.
Значит ллогику можно упростить, разделив ответственность между несколькими методами.

Разнести по разным методам проверку валидности структуры JWT и обработку ошибок редиса.

- Опечатка в аннотации типов в классе `AuthService` метод `authenticate`, `email: str`, а должно быть `email: EmailStr`.

- В роутере `patch_task` есть параметр `id`, лучше не использовать это имя, а назвать более подробно `task_id`.
Имя `id` и так везде повсюду встречается, оно уже зарезервировано как встроенная функция в питоне `id()`.
А чтобы приложение на фронте и дальше смогло отправлять параметр с именем `id` можно заюзать алиас: `task_id: int = Form(..., alias="id")`.

- `confirmPassword: str` не использовать camelCase в питоне для именования переменных. Точно также через алиас решить это.

- Метод `send_daily_report_email` принимает но не использует параметр `user_id`, можно удалить его из сигнатуры метода.

- В методе `process_user_report` дублируется строчка с логированием
`logger.info("Sending request to Kafka for user %s (date: %s)", user.email, target_date)`

- kafka_producer может быть None. А по коду ниже вызываются методы kafka_producer.send() и kafka_producer.flush().

- Зарегистрировался в сервисе с паролем "12345". 
Для сервезных приложений надо заставлять пользователей делать более сложные пароли. 
Надо бы больше логики в методе `verify_password_match` или в отдельный валидатор пароля.

- В классе `ProcessedRequest` есть `correlation_id` с типом `String(255)`.
Крайне редко вижу вообще где-либо использование такого типа данных в постгре, так как мы заранее редко где можем точно знать предельную длину строки в колонке.
Задавая заранее ограничения в 255 символов мы можем создать себе проблемы в будущем, когда понадобится эту длину увеличить.
А никакой практической пользы от использования `String` с ограничением длины строки нет, постгре одинаково работает с ними как и с типом `Text`.
Поэтому если нет особой необходимости, то лучше не использовать такой тип данных, а вибирать просто текст.
А вообще по сути этой колонки там тип данных `UUID` подходит, там же айдишники хранятся.

- Обработка ответа от гигачата. Объект response строго типизирован. Поэтому нет необходимости проверять наличие атрибутов в этом объекте через hasattr.


Общий итог: в целом очень крепкий проект, логично написан. Критических уязвимостей я не нашел.
