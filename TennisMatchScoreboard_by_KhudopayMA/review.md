## Ревью проекта [TennisMatchScoreboard](https://github.com/KhudopayMA/TennisMatchScoreboard)


### Плюсы

+ Деплой жив, на сервис можно зайти, создавать и просматривать матчи.

+ Один и тотже матч можно играть в разных вкладках, при перезагрузке страницы данные обновляются.

+ Типизация в проекте используется.

+ Линтеры ruff и mypy настроены и показывают чистый проект без ошибок.

+ Чистое разделение слоёв: views - services - dtos. 
Вся бизнес-логика счёта вынесена в `ScoreService`, во вьюхах остался только HTTP-слой.

+ Продуманные DTO: `dataclass(slots=True, kw_only=True)` с явной типизацией (`tennis_match_scoreboard/dtos/score_dtos.py`).

+ Защита от гонок при добавлении очка: `select_for_update()` внутри `transaction.atomic()`. 
Счёт не потеряется при параллельном нажатии кнопок.

+ В URL используется UUID матча, а не автоинкрементный id - внутренняя структура БД не светится наружу.

+ `select_related("player1", "player2")` в списке матчей - нет N+1 запросов.

+ Ограничения на уровне БД: `CheckConstraint` "player1 != player2" и "winner in (player1, player2)" - часть инвариантов данных защищена самой БД.

+ CI (`ci.yml`): ruff, mypy strict, typos, pytest с порогом покрытия, MySQL-сервис для тестов.

+ Деплой продуман: healthcheck MySQL, `depends_on: service_healthy`, отдельный nginx, общий volume для статики, миграции и collectstatic на старте.

+ uv + зафиксированный `uv.lock`, в проде `uv sync --frozen --no-dev`.


### Минусы

- Подсчет очков работает не корректно. 
В гейме счет ведется от 0:0, потом 15, потом 30, потом 40 и следующее очко уже выигрывает гейм.
Когда счет 40:40 - это правило ровно, играет до следующих двух очков в пользу одного из игроков.
При счете 30:40 в гейме нажал на 40 и смог получить - `Server Error (500)`.
Точно такой же результат если при счете 40:30 нажать на 40.

- Корневая причина 500-ошибок - модель счёта без 4-го очка. `TENNIS_POINTS = {0:0, 1:15, 2:30, 3:40}`, 
а `_add_standard_point` безусловно делает `inverse + 1`. 
При 30:40/40:30 победа игрока на 40 - `bidict[4]` - `KeyError`. 
По правилам тенниса очко после 40:30 выигрывает гейм, но этот путь в коде не предусмотрен.
Проверка `разница индексов >= 2` до этого кейса даже не доходит.

- При тайбрейке, счет по геймам 6:6, решающий гем играется правильно, но после победы в этом гейме не обнуляется счет в гейме для следующего сета.
И при нажатии на одну из кнопок `score` оно возвращает `Server Error (500)`. Продолжить матч не представляется возможным.

- Тай-брейк - новый сет оставляет грязный счёт гейма. `_add_tie_break_point` при победе вызывает `_add_set`, 
но не `_reset_game()` — очки тай-брейка (например при 7:5) остаются в `current_game`. 
Следующее очко в новом сете - `TENNIS_POINTS.inverse[7]` - `KeyError: 7` - ловим 500.

- Нет валидации имени игрока, смог создать новый матч 
с именем `4444444444444444444444444444433333333333333333333333333333333333311111111111111111111111111111111111`,
поломав немного фронт. Даже такие имена допускаются `!@#$%^&*(_)(*&^` или `(*&^%$%^&*+_`.

- Не использовать `load_dotenv()` на проде. Значение переменной `SECRET_KEY` "прибито гвоздями" прямо в коде. 
Такое допускается только для локальной разработки. При отправке в прод всё это должно быть заменено на энвы из окружения.

- Нет logger совсем. Это довольно важная часть любого проекта. Нам нужно уметь отслеживать ошибки по логам.
Какие входные данные пришли, почему они сломали программу.

- Тесты не покрывают именно баговые сценарии. 
Нет тестов на 30:40, 40:30 и на переход «тай-брейк - новый сет»: 
в `test_win_tie_break_add_point` тай-брейк заканчивает матч сразу (sets 1-2), поэтому грязный счёт не проверяется. 
Порог покрытия 60% в CI (`ci.yml:73`) пропускает такие дыры. Тесты зелёные при явно сломанной логике - ложное чувство безопасности.

- GET match-score: отсутствует обработка `DoesNotExist`. `Match.objects.get(uuid=...)` при неверном uuid получаем 500 вместо 404.

- POST match-score: неизвестное имя игрока молча засчитывается игроку 2. В `_resolve_players` 
else-ветка возвращает player2 как победителя для любого имени, не совпавшего с player1. 
Вместо 400 - начисление очка чужому игроку.

- `MatchesPageView.get` - несколько путей к 500. `int(request_page_number)` - `ValueError` при `?page=abc`; 
`cleaned_data["player_name"]` - `KeyError`, если форма не прошла валидацию (например имя > 100 символов — `is_valid()` вызван, но результат проигнорирован).

- `redirect(url, permanent=True)` 301 Permanent Redirect после POST. Для PRG-паттерна корректно 302; 301 кэшируется браузерами/CDN.

- debug_toolbar включён всегда, а не только при DEBUG: `INSTALLED_APPS` и `MIDDLEWARE`. В проде лишняя нагрузка и утечка отладочной информации.

- `create_match(player1: Player, player2: Player)` - аннотация врёт: принимаются строки из `form.cleaned_data`. 
mypy strict это пропускает только потому, что `cleaned_data` типизирован как `Any`; 
внутри же сервис снова делает `Player.objects.get_or_create(name=...)`.

- Player.name без `unique=True`. `get_or_create` при параллельных запросах может упасть с `IntegrityError`.

- compose.yaml: MySQL-контейнеру не передаются `MYSQL_USER`/`MYSQL_PASSWORD` - создаётся только root. 
Если в `.env` `DB_USER != root`, приложение не подключится к БД. 
Healthcheck при этом использует `${DB_USER}` то есть `root`.

- Dockerfile: uv ставится через `curl | sh` без пиннинга версии - образ не воспроизводим. Всегда надо указывать точный тег для любых образов и либ.
В `.dockerignore` не исключены `.git`, `.venv`, кэши - раздутый build context.

- CI: `ruff format` без `--check` - форматирование фактически не контролируется: раннер просто переформатирует файлы без падения сборки.
Обычно `ruff format --check --diff` чтобы увидеть что не прошло и почему.

- `.env.example` не содержит `SECRET_KEY` - секрет невозможно задать через env, поэтому он захардкожен в коде. 
Даже при желании «вынести в энвы» переменной для него нет. `ALLOWED_HOSTS` тоже захардкожен и не конфигурируется.

- README расходится с кодом: бейдж «Django 5.0», при этом settings сгенерирован Django 5.2.15, а миграция - 6.0.6; 

- Проект написан на python, а ссылка в футере сайта на java-роадмап.


### Итог

В проекте есть много плюсов, чистая архитектура, понятная структура проекта. 

Но также много минусов, некоторые из них критичны, требуется доработка.
