## Ревью проекта [DRFiles](https://github.com/AntonFeoktistov/DRFiles)

## Общее впечатление

Архитектура чистая и логичная: view, service, repository, работа с S3 вынесена в отдельный `MinioService`, 
каждая операция (`upload/delete/move/download`) — в свой сервис. 
Метаданные в `Postgres`, контент в `MinIO` - классическая схема. 
Есть интеграционные тесты с `Testcontainers`, Swagger-документация, docker-деплой. 
Структура кода поддерживаемая.


## Плюсы

+ Сервис в деплое работает, получилось зарегистрироваться и залогиниться, можно добавлять директории и файлы.

+ Настроен автодеплой через docker, хорошая практика использовать `entrypoint.sh` для запуска бекенда

+ Чистое разделение слоёв: view - сервис - репозиторий. 
Сервисы получают зависимости через конструктор `UploadService(self.minio, self.repo)`, это удобно для тестирования.

+ Хороший набор интеграционных тестов: покрыты все операции (auth, upload, get, delete, move, download, search), 
включая изоляцию между пользователями и «краевые» случаи (пробелы, кириллица, вложенные папки).

+ `unique_together (user, full_path)` + индексы на `(user, full_path)` и `(user, folder)` - правильная защита от дублей на уровне БД.

+ JWT-blacklist через Redis: токен логируется по `jti` с TTL, равным оставшемуся времени жизни токена, 
а не «навсегда» - в Redis не копятся мусорные ключи. Валидация в `CustomJWTAuthentication` аккуратная.

+ `MinioService` - синглтон, boto3-клиент создаётся один раз на воркер.

+ OpenAPI-документация через drf-spectacular с кастомным security extension.

+ Dockerfile: отдельный non-root пользователь, healthcheck'и и `restart: unless-stopped` в compose. Всё это хорошо.

+ Единый обработчик ошибок и свой `ConflictError` с 409 - консистентный формат ответов об ошибках.

+ Типизация активно используется.
+ 

##  Минусы

- Конструкцию с `load_dotenv()` лучше не использовать, даже для локальной разработки, тем более на проде.
Хотя может быть в джанге это и является номальным способом.
Есть в FastAPI способ извлекать и хранить эти переменные в дата классах, пример:
```python
from pydantic import BaseModel
from os import environ as env

class S3Config(BaseModel):
    url: str = Field(alias="S3_URL")
    access_key: str = Field(alias="S3_ACCESS_KEY")
    secret_key: str = Field(alias="S3_SECRET_KEY")
    bucket: str = Field(alias="S3_BUCKET")

class Settings(BaseModel):
    s3: S3Config = S3Config(**env)
```
Может что-то такое есть в джанго? По крайней мере централизация всех переменных окружения явно просится через отдельный объект настроек.

- Логирования нет. В самых узких местах, где возможны ошибки надо выстраивать систему логирования.
Чтобы по логам можно было определить какие были запросы и почему они сломались. Это довольно важная часть бекенда обычно.

- По коду много где встречается, что метод объявляется как метод экземпляра класса с `self` первым аргументом, но нигде этот `self` потом не используется.
Здесь надо посмотреть и проверить каждый такой метод на выполняемый им функционал. 
Точно ли он не является свойством объекта.

- Конфигурация и безопасность.
Рассинхрон имён env-переменных. 
В `.env.prod.example` переменная называется `DjangoSECRET_KEY`, а `config/settings.py` читает `SECRET_KEY`. 
Причем такого нейминга лушче вообще избегать - `SECRET_KEY`, что за секретный ключ, от чего он, понять невозможно.
Лучше пусть чуть длинее будет имя, зато сразу всем понятно от чего оно - `DjangoSECRET_KEY`.

- `DEBUG = os.getenv("DEBUG", "True") == "True"` по умолчанию `DEBUG` включён, обычно по умолчанию `False`.

- `SESSION_COOKIE_SECURE = False` даже в проде, если куки когда-нибудь понадобятся, они будут ходить по http.

- Пароль в `RegisterSerializer` — `min_length=2` (`users/serializers.py`). 
- `AUTH_PASSWORD_VALIDATORS` объявлены в settings, но через API не применяются, create_user не валидирует пароль.
Такии образом я смог создать нового пользователя со следующими значениями:
```bash
curl -X POST "http://201.24.125.74/api/auth/sign-up" \
  -H "Content-Type: application/json" \
  -d '{"username": "ta", "password": "12"}'
```
Ответ пришел с токеном:
```bash
{"refresh":"eyJhbGci...
```
Хотя фронт валидирует длину имени и пароля в 3 и 6 символов соответственно.

- Нет троттлинга/rate-limiting на auth-эндпоинтах (`sign-in` можно перебирать пароли без ограничений). 
В учебных проектах конечно никто об этом не думает.

- Гонки: проверка уникальности username в сериализаторе, а потом `create` — при двух одновременных регистрациях одна упадёт в `IntegrityError` 500. 
То же для создания папок и файлов (unique_together на уровне БД не превращено в 409).

- Модель данных и БД.
`name` в `Folder`/`File` продублирован с `full_path` и синхронизируется вручную (например, в `move_service` меняются оба поля). 
При этом `ResourceResponseSerializer` имя вычисляет из `full_path` заново 
То есть хранимое `name` избыточное поле, которое легко рассинхронизировать. Либо убрать, либо сделать его единственным источником истины.

- Поиск через `name__icontains=query` - не использует индексы, при росте объёма данных деградирует до полного скана. 
Плюс к этому поиск и листинг директории возвращают всё без пагинации - большая папка или пустой LIKE-фильтр выгрузят всё в память и в JSON.

- `File.size` - `IntegerField` (2 ГБ потолок), лучше с запасом использовать `BigIntegerField`.

- Сервисный слой и работа с MinIO.
Несоответствие исключений — мёртвый `except`. 
`delete_service.py` ловит `S3Error` из пакета `minio`, но `minio_service.py` использует `boto3`, который бросает `botocore.exceptions.ClientError`. 
Ветка `except S3Error` никогда не сработает, а реальные ошибки MinIO (не 404) улетят как ClientError в 500. 
То же в `move_service.py` ловится `ClientError` - а его выбрасывает уже сам `minio_service`, причём оборачивая в голый `Exception`.
При работе с файлами и папками через клиента можно максимально точно отловить какие ошибки оттуда могут приходить.
Здесь же в классе `MinioService` в ините происходит работа с переменными оркужения:
`self.bucket_name = os.getenv("MINIO_BUCKET_NAME", "user-files")`
лучше всю работу по извлечению переменных окружения делать в файле `config.py` или `settings.py`, и оттуда уже забирать в нужные сервисы уже готовые значения.

- Голые `raise Exception` теряют traceback и детали: 
`minio_service.move_file` и `move_service.move_folder`, `delete_service`, `download_service`. 
Отладить такой сбой будет затруднительно, а все ошибки схлопываются в 500. 
Нужны свои исключения (или перехват конкретных типов) с `raise ... from e`.

- Неатомарность «MinIO + БД». 
`upload_files` обёрнут в `@transaction.atomic`, но запись в S3 не откатывается при падении коммита в БД - остаются зависающие объекты в бакете. 
Удаление и перемещение — аналогично. Нужен компенсирующий шаг (cleanup при ошибке) или фоновый сборщик мусора.

- `download_folder` собирает весь zip в памяти (`io.BytesIO`) - большая папка уронит воркер. 
И при ошибке чтения файла делает `except Exception: continue` - файл молча пропадает из архива без всякого логирования.
Тут надо строить zip потоково, добавить логирование ошибок + вывод об ошибках пользователю на фронт.

- `minio_service.upload_file` принимает `str` путь к файлу и делает `open(file_obj, "rb")`
в проде это потенциальный путь для чтения произвольных файлов изнутри процесса, по приколу можно попробовать прочитать любой файл на сервере.

- `StorageService.__init__` при каждом запросе строит все 5 сервисов, 
а первый вызов `get_minio_service()` выполняет `head_bucket`/`create_bucket` (сеть) прямо во время запроса - это лучше делать при старте воркера.

- API и роутеры
Copy-paste баг: `storage/urls.py` — `app_name = "users"` (должно быть `"storage"`).
Copy-paste в схеме: `resource_view.py` - на `GET /api/resource` навешан `@extend_schema(request=upload_request, parameters=upload_parameters)`, 
описывающий multipart-загрузку. У GET нет тела - документация вводит в заблуждение.

- Дублирование auth-эндпоинтов: свои `sign-in`/`sign-out` + простые JWT-эндпоинты `/api/auth/api/token/{refresh,verify}` 
с кривым неймингом (`/api/auth/api/token/...`). Либо оставить одно, либо убрать дублирующие.

- Всё состояние (перемещение, удаление, создание) через query-параметры, а не через body - для перечислений это допустимо, 
но `POST /api/resource/move?from=...&to=...` уже на грани; длинные пути с кириллицей будут упираться в лимиты URL.

- Авторизация и кеширование.
`LogoutView` принимает refresh-токен в теле и сразу валидирует `RefreshToken(refresh_raw)`
если токен уже просрочен/невалиден, будет 401/400 вместо 204, что не критично, но лучше явно обработать.

- Деплой.
- `entrypoint.sh` выполняет `pip install mc` прямо при старте контейнера - пакет нужно класть в образ на этапе сборки. 
Каждый рестарт = установка пакета из сети, долго.

- `minio/minio:latest` без пина версии (и в compose, и в testcontainers) — невоспроизводимость окружения.
Лучше забыть навсегда про использование тега `latest` и всегда указывать точные версии.

- В тестах очень много где создаются переменные, но потом нигде не используются.
Напримет тут `parent = factory.create_folder(auth_client, test_user, "parent/")`,
здесь если требуется выполнить функцию, то результат её выполнения не обязательно присваивать переменной.


Общая оценка: хороший крепкий уровень для учебного проекта, к проду требуется доработка по безопасности и отказоустойчивости.
